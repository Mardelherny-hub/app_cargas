## Diagnóstico de solo lectura previo al código

1. **Embalaje de ítems:** no hay columna específica de tipo de embalaje. En `BLS!Q` (`DESCRIPCION MERCADERIA`), 7 BL dicen `CARTONS`, uno dice `Fardos` y 67 no identifican tipo de embalaje de forma explícita. El catálogo activo **real de la base B** tiene 4 nombres: `A GRANEL`, `CONTENEDOR`, `NO RETORNABLE`, `RETORNABLE`. Ninguno equivale con certeza a CARTON/FARDO. Antes el parser usaba **CONTENEDOR** para `shipment_items.packaging_type_id` sin respaldo en la mercadería. Ahora detecta solo textos inequívocos CARTON/FARDO y busca equivalencia exacta activa; si no existe, deja `shipment_items.packaging_type_id = null` con advertencia por BL. También deja nulo el primario del BL dentro del parser, **pero el Job `ProcessManifestImportJob::applyContainerPrimaryTypes()` aplica la regla global `CONTENEDOR` al BL contenedorizado después**. No se alteró esa regla global ni otros formatos. El resultado solicitado es el campo del **ítem**, no el primario genérico del BL.
2. **NCM:** la muestra **sí tiene una columna específica**: `BLS!G` (`NCM`), con 75 valores. Se prototipó la regex sobre el texto real de `BLS!Q` de los **75 BL**: **cero coincidencias** de NCM/HS explícito. No hay base para extraer códigos de Q en esta muestra. El parser ya copiaba G, pero aceptaba los **9 valores `0000.00`/`0000.000`** como si fueran códigos. Ahora se conserva G cuando tiene un código identificable (**66 BL**), y esos nueve quedan `null` con advertencia. Para futuras variantes, solo se lee un código **etiquetado explícitamente** (`NCM:` o `HS CODE:`) desde Q cuando G no aporta uno inequívoco; más de una aparición o conflicto entre G/Q produce `null` y advertencia. Ninguna cifra libre de la descripción se trata como NCM.
3. **Condición de contenedor:** en `CONTENEDORES!A:I` no existe columna para condición House/Puerto. `Container::CONDITION_HOUSE_TO_HOUSE = 'H'` y `CONDITION_PORT_TO_PORT = 'P'`; `L`/`V` son otros estados operativos. Antes, por defecto de tabla, las unidades quedaban documentalmente en `P`, los ítems en `null`. Ahora se asigna `H` en contenedor nuevo, ítem y vínculo. **No se modifica `condition` operacional**, preservando `V` para vacíos y `L` para llenos. Para un contenedor previamente existente se respeta su condición documental válida `H`/`P` en el vínculo. Esta muestra no permite probar condición **declarada por el archivo**: no hay columna correspondiente.
4. **Notificatario:** `BLS!A:Q` no tiene campo específico. Antes `bills_of_lading.notify_party_id = null` en los 75. Ahora el valor por defecto es el mismo cliente ya resuelto en `Cnee` (`BLS!K`), para los 75. No se crea un cliente adicional.
5. **BL `DT0626SMSCCAA22`:** `BLS!A30` número, `J30=K30=MEDITERRANEAN SHIPPING COMPANY S.A.`, `Q30=VACIOS MSC`, `P30=80`, `G30=0000.000`. En `CONTENEDORES` hay 80 filas para ese BL. En la importación previa **el parser ya guardaba cargador y consignatario**, ambos cliente existente id 751, y la UI deduce transporte propio cuando son iguales (`BillOfLadingEditForm`). **La falta de esas dos partes reportada en Stage no se reproduce en esta base y SHA**; no se inventó una causa ni un cliente sustituto. El notificatario sí estaba vacío: después también queda con id 751. Condición documental H en las 80 unidades y operativa V (vacíos).
